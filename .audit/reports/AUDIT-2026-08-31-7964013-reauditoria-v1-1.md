### F-001 — Rama `main` declarada pero inexistente

**Descripción**: `AGENTS.md`, sección "Git", describe en tiempo presente:
"Rama de producción: `main` — solo recibe merges desde `develop` vía PR,
cuando se decide hacer un release". La sección "Setup manual" presupone
que `main` ya existe ("hacer el primer push de `main` y `develop` es un
paso manual del humano"). `docs/tecnica/operational-readiness-docs.md`
("Por qué `develop` y no `main`") también presupone su existencia. En el
repositorio real: `git branch -a` no muestra ninguna rama `main`, local
ni remota, en ningún punto del historial visible; la rama default
configurada en GitHub es `develop` (`gh api ... --jq .default_branch` =
`develop`).

**Impacto**: `TEMPLATE.md` lista explícitamente "Use this template" como
mecanismo de reutilización soportado. Ese mecanismo de GitHub copia por
defecto la rama default del repositorio origen (salvo que el usuario
marque "Include all branches", una opción no mencionada en ningún punto
de la documentación de este template). Un consumidor nuevo que siga el
mecanismo documentado terminaría, con alta probabilidad, con un
repositorio que reproduce exactamente este mismo estado — sin `main` —
sin que el "Setup manual" documentado explique cómo resolverlo (asume
que ya existe algo que pushear).

**Causa raíz**: nunca se creó una rama `main` en este repositorio, ni
siquiera como snapshot inicial vacío o como copia de un estado previo a
`develop`; consistente con que el proyecto "no tiene producto propio
todavía" (ROADMAP.md) y por tanto nunca hubo una decisión de release,
pero esa ausencia física de la rama nunca quedó documentada como una
decisión o un paso pendiente explícito.

**Corrección mínima suficiente**: dos caminos válidos, a decisión
humana (no algo que un agente deba resolver unilateralmente):
1. Crear la rama `main` ahora (por ejemplo, desde el estado actual de
   `develop`, o desde un commit inicial vacío/mínimo), documentando en
   `AGENTS.md`/`arquitectura.md` en qué estado queda y cuándo empieza a
   recibir merges reales; o
2. Reformular explícitamente `AGENTS.md` (sección "Git") y
   "Setup manual" para dejar constancia de que `main` es, por diseño,
   una rama diferida hasta el primer release real, agregar ese paso a
   la lista de "Setup manual" (creación de `main` como parte de la
   adopción, no solo su "primer push"), y ajustar el README para que
   PASO 1 no presuponga una rama `main` que no existe en el propio
   template.

**Verificación de cierre**: `git branch -a` debe mostrar `main` (opción
1) o `AGENTS.md`/README.md deben describir explícitamente el estado
diferido y el paso de creación manual (opción 2), sin contradicción con
"Setup manual".

**Puntos recuperables**: +3.75 (Q1.3 +0.75, Q2.1 +1.50, Q4.2 +0.75,
Q6.1 +0.75).

### F-002 — `docs.yml`/GitHub Pages nunca ejercido y actualmente inalcanzable

**Descripción**: `docs.yml` se dispara únicamente con `push: branches:
[main], paths: ["docs/**", "mkdocs.yml"]`. `gh run list
--workflow=docs.yml` no devuelve ninguna corrida histórica. `gh api
repos/.../pages` devuelve 404 (GitHub Pages no configurado). Downstream
directo de F-001 (sin `main`, el trigger nunca puede evaluarse).

**Impacto**: `AGENTS.md`, sección "CI/CD", presenta `docs.yml` como
parte de la infraestructura actual del proyecto ("se dispara al pushear
a `main`... Publica el sitio MkDocs a GitHub Pages"), sin calificarlo
como pendiente o prospectivo. El build subyacente sí es reproducible
(`mkdocs build --strict` exitoso, ver V-15), por lo que el problema es
específicamente de disparo/publicación, no de contenido.

**Causa raíz**: ROOT-001 (ausencia de `main`) + GitHub Pages nunca
configurado (paso manual ya listado en "Setup manual", pero sin
relación explícita con la ausencia de `main` documentada en ningún
lugar).

**Corrección mínima suficiente**: resolver F-001 (lo que habilita que
`docs.yml` pueda dispararse) y completar el paso ya documentado en
"Setup manual" (Settings → Pages → Source → GitHub Actions).

**Verificación de cierre**: una corrida real de `docs.yml` con
`conclusion: success` tras el primer push relevante a `main`.

**Puntos recuperables**: +0.75 (Q1.2).
